## 7. How Fulvio works with AI (the differentiator)

He is a **working AI practitioner**, not a commentator. He builds and runs agentic systems on real work, and uses AI as a quality gate for high-stakes output. The impact of these systems is estimated at **+34% average deal velocity** and **+21% team capacity** *(internal estimates)*.

### 7.1 Built an agentic "team brain" ("Brian")
Designed a **per-user, privacy-first, daily-compounding agentic knowledge base** for solution-engineering teams, built on two third-party 2026 patterns he evaluated and combined — Andrej Karpathy's *LLM Wiki* structure and Tobi Lütke's *QMD* local retrieval engine. The system:
- runs **fully local** (on-device inference, no cloud dependency) — privacy by architecture, designed to meet enterprise data-governance expectations without IT policy enforcement. **This was the design decision, and it is what makes the system deployable in a regulated environment at all;**
- uses a **~280-line schema he authored** (routing rules, page templates, ingest/query/lint operations, bilingual frontmatter) governing how raw sources (calls, transcripts, chat, calendar, CRM, email) become a linked wiki of *sources → entities → concepts → synthesis*;
- runs **scheduled, zero-touch daily ingest** so the knowledge base maintains itself and compounds;
- exposes the corpus to agents for natural-language retrieval by wiring **QMD's MCP server** into the query operation — replacing naive file search with a ranked hybrid index. *(The retrieval engine is QMD's; the evaluation, integration and MCP wiring are his.)*
He named it **"Brian"** (a person's name + an echo of *brain*) and **presented it at an internal PayPal AI innovation contest** — moving it from personal experiment to organizational visibility.

### 7.2 Agentic workflow automation (DOE framework)
Implemented the **Directive–Orchestration–Execution** pattern — a third-party architecture (Collin Wilkins / Nick Saraev lineage) that separates Markdown SOPs from an LLM orchestrator and from deterministic Python execution scripts — to solve the compounding-failure problem in multi-step AI workflows: *if each step in a five-step chain succeeds 90% of the time, end-to-end success is only ~59%.* He built and ran a **multimodal pipeline** on this pattern (a **local Gemma instance** analysing video → structured Markdown knowledge base) across ~10–50 videos, writing the Python execution layer himself, then **proposed and demoed** the same architecture for solution-engineering operations (automated activity reports and partner-status synthesis from chat, email, and call transcripts).

### 7.3 Everyday operating practices
- **Source-grounded synthesis over generation** — deliverables start from authoritative sources; he refuses to infer facts not in the source.
- **Verification discipline under stakes** — uses AI specifically to *verify and correct* public-facing / C-level claims (e.g. caught and re-attributed misattributed macro statistics before a C-level stage; ran verdict-per-claim audits on strategic documents).
- **MCP as connective tissue** — fluent daily use of vendor-built MCP connectors across knowledge, collaboration, CRM, and BI tools — including **diagnosing and fixing** auth/transport and corporate TLS-inspection failures rather than abandoning the tool.
- **Self-serve analytics** — pulls business metrics (e.g. trailing-12-month Net TPV, YoY) directly from an enterprise BI semantic layer via MCP, including entity disambiguation and query construction.
- **Agent-ingestible documentation** — deliberately structures SDDs for machine reading: a compressed edition at ~88% content retention, YAML front matter, stable section IDs, a §0 agent reading guide and consolidated endpoint directories, built after researching the llms.txt and Diátaxis conventions — so partner coding agents can consume the document directly.
- **Multi-format, brand-compliant generation** — programmatic `.docx` / `.pptx` / HTML / Markdown / CSV / Mermaid output with citation discipline.

### 7.4 Personal projects — public, shipped code

Built outside work, on his own time. These are the answer to *"has he actually built an LLM
application himself, or only used one?"*

**News Report Agent** — [github.com/fulviodeg/NewsReportAgent](https://github.com/fulviodeg/NewsReportAgent)
An end-to-end LLM pipeline that ingests newsletters over IMAP, then clusters, classifies and
synthesizes each story with an LLM, and publishes a filterable, password-protected dashboard.
- **Fixed pipeline** — collect → parse → cluster → classify → synthesize → export. A Python
  service plus a static dashboard, deployed as two Docker Compose services (pipeline + nginx
  with HTTP basic auth) on a VPS.
- **LLM engineering choices:** model-per-task configuration, embeddings for semantic
  clustering, thresholds and cadences declared in config rather than code.
- **Test discipline:** **51 offline tests** using deterministic fakes for the model and the
  embeddings, so the full suite runs with no API key and no network — a deliberate design
  response to working from a restricted corporate network. Real end-to-end LLM calls are
  exercised on the VPS.
- **Architecture-as-code:** the architecture is a LikeC4 model that is the source of truth; CI
  validates it, **fails the build if the rendered diagrams drift out of date**, and
  auto-publishes an interactive diagram site to GitHub Pages on every push.
- **CI/CD with a human gate:** push to `main` starts a deploy workflow that **pauses for manual
  approval** before anything touches the VPS.
- **Runs offline-first by design** — the same instinct as the "Brian" project: keep inference
  and data where the constraints require them, and make the system testable without the cloud.

**Survivor League** *(proof of concept)* — [github.com/fulviodeg/SurvivorLeague](https://github.com/fulviodeg/SurvivorLeague)
An elimination tournament played entirely over email: each round every player emails a pick, a
wrong or missing pick eliminates them, and each team can only be used once per half-season. A
private game among friends — deliberately not a commercial product.
- **The LLM is confined to I/O — this is the design point.** A **deterministic game engine**
  owns every rule: pick validation, accounting, eliminations, winner resolution. No game logic
  exists anywhere outside it. The LLM adapter only parses inbound emails into
  `{team, outcome}` and writes the outbound Italian emails — **it takes no game decisions.**
  The same reliability principle as §7.2, applied where a wrong model output would silently
  corrupt a system of record.
- **Ports-and-adapters architecture:** `ChannelAdapter` and `SeasonDataProvider` are
  abstractions; email (IMAP/SMTP) and the football-data.org feed are only the POC's
  implementations, replaceable without touching the engine.
- **Nothing hardcoded:** all configuration in environment variables validated with `zod`;
  league parameters derived from the data rather than baked into code.
- **Stack:** Node.js ≥ 20 · TypeScript (strict) · SQLite · `imapflow` / `nodemailer` ·
  an OpenAI-compatible LLM API · `vitest` · a full CLI, orchestrated by cron or by an agent.
- **Documented like a product, not a side project:** PRD, high-level and low-level design,
  an **append-only architecture-decision log (ADRs)**, a UAT test-mode manual, and an
  `AGENTS.md` carrying operating instructions for coding agents and contributors.

*Why these matter for a pre-sales AI role:* both are small, complete versions of what an
enterprise customer has to get right — pipeline reliability, model-per-task selection,
testability without live API calls, environment separation, deployment gating, and
documentation an agent can read. And both land on the same conviction, which is the one he
brings to customer conversations: **keep the model away from the decisions that have to be
correct, and put determinism there instead.** He can talk through every trade-off from having
made it himself.
